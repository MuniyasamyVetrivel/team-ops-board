# Team Ops Board: Phase 1 (Repo Inspection) + Phase 2 (Architecture & DB Design)

## Context
`docs/PROJECT_BRIEF.md` specifies an "Internal Work & Performance Management System" (tasks, workload, help desk, projects, approvals, collaboration, reports, admin, and a large Digital Marketing performance module) so Rakesh, the Super Admin, can see team workload and marketing performance at a glance. The user asked for **Phase 1 + Phase 2 only**: confirm the repo state, then propose folder structure, the full MySQL schema with Flyway migration order, and a phase-by-phase plan. **No application code is written in this step.** Constraints: Java 21, latest stable Spring Boot, MySQL on `localhost:3306` (db `team_ops_board`, user `teamops`). Credentials live in `.env` only and are never hard-coded or committed.

These decisions supersede the plan text below:
- **Versions:** Spring Boot **4.1.1** (latest GA; 4.2.0 is still at milestone 2), TypeScript **6.0.x** (typescript-eslint doesn't support 7 yet), React Router **8**, Vite **8**, jsdom **29** (30 needs Node 24.15+).
- **IDs** are signed `BIGINT`, not `BIGINT UNSIGNED`. Signed ids map to Java `Long` and avoid signedness mismatches on foreign keys.
- **Dev seed data** is switched on with `DEV_SEED_ENABLED=true` in `.env`, not with a `dev` Spring profile, because a `.env` property can't activate profiles. The `dev` profile only adds verbose logging.
- **Integration tests** use the local MySQL, run with `mvnw verify -Pit` (`*IT.java`). Testcontainers was not added.
- **Schema/entity mapping rules** (enum `VARCHAR`, no `CHAR`, `columnDefinition` for `TEXT`/`JSON`) are recorded in `CLAUDE.md`.
- **MapStruct was not added.** DTOs use small static `of(...)` factories, which are simpler at this size.
- **The user admin UI assigns one role per user** (Super Admin, Department Manager or Employee), plus direct permission grants. The backend still accepts a set of roles.
- **Workload includes undated open tasks** (as well as overdue tasks and tasks due within the window), so undated work can't hide an overload. Status, priority and date filters only narrow the count columns. The Completed column defaults to the last 30 days.
- **"Today" is evaluated in a business time zone** (`APP_TIME_ZONE`, default Asia/Kolkata), and the server sends each task's `dueState`.
- **`projects.progress_override` is `INT`** rather than `TINYINT`, which keeps schema validation simple; a CHECK constraint keeps it within 0–100.
- **Every sort puts empty values last** (`PageRequests`), for example undated tasks.
- **No new migrations in Phase 4.** V1 already created `department_members`, `user_permissions` and the other identity tables.
- **Phase 6 dashboard is one endpoint for every role**, scoped by `AccessScope`; dashboard counts use the viewer's *work* (`TaskSpecifications.workOf`: managed departments plus own assignments), not every task they can open. Ticket/SLA/approval KPIs are `null` until their phases; the marketing summary waits for Phase 19.
- **Recent activity comes from `task_history`** (scoped through the task), not `audit_logs`, so managers and employees get a meaningful, permission-safe feed.
- **`notifications.dedup_key`** (unique per user) makes the daily reminder job idempotent. `calendar_events` gained `version` (optimistic locking) and stores all-day events as business-zone midnights.
- **The calendar API ships in Phase 6 with task deadlines and events only.** Project milestones and approval deadlines join it in Phase 8 with their modules.
- **SLA warning threshold is global** (`sla.warningThresholdPct` in `app_settings`), not per policy, and is snapshotted on each ticket with the due times (`sla_warning_pct`). `sla_policies` has one row per priority and no `active` flag. Tickets store an explicit `sla_start_at`.
- **SLA states are ON_TRACK / WARNING / BREACHED per deadline**, plus `met` (null while open) and `paused` flags. The SLA clock also pauses between resolve and reopen, so time spent resolved never counts. A priority change does not move due times.
- **Tickets are routed to a handling department** by category (`ticket_categories.default_department_id`). Help desk agents are users with `TICKET_EDIT` in that department; employees do not get it by role.
- **Approvals copy the workflow on submit** (`approval_steps` per request), so workflow edits never change requests in flight. Step states are WAITING / PENDING / APPROVED / REJECTED / SKIPPED. Self-approval is impossible: a USER step naming the requester is skipped, a department-manager step escalates to the Super Admin role when the requester is the manager (or there is none), and consecutive steps for the same role collapse. `approval_attachments` was not added (not in the brief).
- **Announcement receipts** are written with idempotent SQL (`INSERT IGNORE` / upsert keeping the first read and acknowledgement). The audience is the viewer's primary and managed departments; secondary memberships do not add announcements. Scheduled announcements notify nobody when they go live (no scheduler for that yet).
- **Knowledge base editors** (`KB_EDIT`) may edit any article: it is shared knowledge. Slugs are fixed at creation (unique with a numeric suffix). `view_count` is the only stored counter.
- **Documents** store `current_version_no` instead of a `current_version_id` FK (avoids a circular FK); versions are numbered 1..n and never deleted individually.
- **Project members and dependencies** are mapped as link tables; `project_members.project_role` stays NULL. `project_attachments` is unused: project files live in Documents (`documents.project_id`).
- **Optional boolean request fields are nullable** (`Boolean`, defaulting to false): Jackson 3 rejects missing primitives, which made omitted flags a 400.
- **Ticket search uses LIKE on subject and code**, consistent with tasks; the planned FULLTEXT index was not added. SLA figures are computed in Java with `SlaCalculator` over the viewer's tickets, so the list, SLA page and dashboard always agree.
- **No migration in Phase 9.** The marketing tables arrive with their modules (V9 in Phase 10). The CSV import is stateless: the preview returns a SHA-256 checksum and the commit re-uploads the same file and re-validates it, so no staging table is needed.
- **Ranking change when a month is Not Ranked**: NR → ranked counts as IMPROVED and ranked → NR as DECLINED, with no numeric change; no previous row at all is NEW.
- **SEO statistics are per selected month, computed from the history rows** for that month and the month before (`SeoRankingQuery` + `KeywordStanding` + `SeoStats`), not from the keyword cache. A keyword with no row for the month counts as Not Ranked ("position unavailable") and is also reported as `notRecorded`; it has no movement. Archived keywords are left out of page statistics. The `current_position`/`previous_position`/`last_ranked_at` cache is maintained by `SeoKeywordRepository.refreshRankingCache` (used by the seed now, and by ranking entry in Phase 11).
- **SEO data is shared across the Digital Marketing team**, not department-scoped: SEO_VIEW reads every page and keyword, SEO_EDIT changes them. Owners must be active users holding MARKETING_VIEW. Pages with keywords and keywords with ranking history cannot be deleted (409), only archived; archived pages take no new keywords. Positions and month columns are `INT` (not `SMALLINT`/`TINYINT`) to keep schema validation simple; keyword location is NOT NULL (default "India") so the unique key works.
- **Ranking corrections are limited to open months**: a month's own row can be corrected (PUT with `version`, audited with from/to) only while it is the current business month or the one before; older months return 409 `MONTH_LOCKED`, except to a Super Admin, who may correct any past month (still audited, with `closedMonth: true` in the audit details). Each history entry's `correctable` flag is evaluated for the viewer. Recording never overwrites: a month that already has a row returns 409 `RANKING_EXISTS` (single, monthly update and CSV). Future months are rejected. A correction or a backfilled month also refreshes the *next* month's `previous_position`/`ranking_change` snapshot (never its position), and the keyword cache is refreshed after every change.
- **The monthly update is all or nothing** (at most 500 keywords): if any keyword already has the month, nothing is saved. Manual recordings write one `SEO_RANKING_RECORDED` audit entry each; CSV imports are covered by the single `CSV_IMPORTED` entry.
- **CSV rankings import** (`seo-rankings`) matches keywords by page URL + keyword + engine + location + device, ignoring case. Position is required ("NR" for Not Ranked), so a blank cell is never stored as Not Ranked. Rows are inserted oldest month first so snapshots are right.
- **The SEO ranking table is native SQL** (`SeoRankingTableQuery`) because its filters and sorts depend on the month's history rows; it returns a page of ids and the rows are loaded in two batched queries. Sort keys are whitelisted.
- **Target actuals**: a type's `actual_source` decides where its actual comes from. A `TargetActualSource` bean per source computes it (Keywords in Top 10 = keywords not archived recorded at 1–10 for the month, matching the SEO summary; Landing Pages Created = LANDING_PAGE pages created in the month, business time zone). Sources whose module does not exist yet (leads, backlinks, blogs, email and paid campaigns) take a hand-entered actual until then. **A stored hand-entered actual always wins**, so months recorded by hand before a source became automatic never change; new manual actuals on an automatic type are rejected (400 `ACTUAL_IS_AUTOMATIC`).
- **Target history**: one target per type and month (409 `TARGET_EXISTS`). Targets can be set and changed for the previous business month onwards (future months are planning); older months are locked (409 `MONTH_LOCKED`) except to a Super Admin, the same window as ranking corrections. Future months are "planned": no actual (400 `FUTURE_ACTUAL`), no achievement and no status. Changes are audited with from/to.
- **Target types** are managed with MARKETING_EDIT (Super Admin and the marketing manager). Once a type has targets its unit, actual source and lead source are fixed (409 `TYPE_IN_USE`) and it can only be deactivated, not deleted. The behind threshold is per type or the global `marketing.target.behindThresholdPct` (60%); counts must be whole numbers and percentages at most 100. Trend buckets add counts and money and average percentages over the months that have a target; the YEAR view shows five years.
- **Recurring activity periods follow the calendar**: a day, an ISO week (Monday–Sunday), a month, a quarter or a year (`Recurrence`). An occurrence is due `due_offset_days` after its period starts, clamped to the period's last day. Task titles fill `{month}`, `{year}`, `{quarter}`, `{week}`, `{date}` and `{period}`. Overdue/due-soon is computed (`DueState`), so occurrence statuses are only PENDING, IN_PROGRESS, COMPLETED and SKIPPED (no stored OVERDUE).
- **Occurrence lifecycle**: creating or reactivating an activity creates the current period's occurrence (earlier periods are not backfilled); the daily job (`MARKETING_ACTIVITY_CRON`, 00:10 business time) does the same for every active activity. Closing an occurrence creates the following period's, while the activity is active and its dates cover it; the unique key (activity, period start) makes every path idempotent. An occurrence with a task follows it: completed → COMPLETED, cancelled → SKIPPED (both create the next), any active status reopens it (the next one is kept). Occurrences without a task (no title template) are completed, skipped or reopened on the activity by its owner, assignee or a marketing manager. Frequency and start date are fixed once an activity has occurrences; an activity with history is deactivated, not deleted.
- **Activity notifications reuse existing types** for now: generated tasks send TASK_ASSIGNED and then get the normal task reminders; task-less occurrences get TASK_DUE_SOON / TASK_OVERDUE (entity `MARKETING_ACTIVITY`) from the daily job, once per occurrence and due date. The current notification bell has no fallback for unknown types, so dedicated activity types wait for the Phase 13 frontend.
- **Migrations ship per phase, so numbering moved on from the table above**: V12 is `V12__marketing_email_campaigns.sql` (email only); paid campaigns and their monthly metrics get their own migration in Phase 15, and the later files shift by one.
- **Email campaigns store raw counts only**, which belong to SENT campaigns (400 `COUNTS_NEED_SENT` otherwise); a sent campaign cannot be dated in the future, cannot be deleted (409 `CAMPAIGN_SENT`) and counts in the month of its campaign date. Counts must be consistent (delivered ≤ sent, unique ≤ total, unique opens/clicks and unsubscribes ≤ delivered), checked in `EmailCounts` and by table CHECKs. Rates follow brief §80: open = unique opens ÷ delivered (8,500 ÷ 24,000 = 35.42%), click = unique clicks ÷ delivered, lead conversion = leads ÷ delivered, plus delivery, click-to-open, bounce and unsubscribe rates; monthly and per-type rates are computed from the summed counts (weighted), never averaged. The brief's §39 example (34% = opens ÷ sent) uses a different denominator; CLAUDE.md's formula wins.
- **Paid campaigns separate the plan from monthly results.** A campaign holds dates and budget; results (spend, impressions, clicks, leads, conversions) are recorded per month in `paid_campaign_metrics` (unique campaign + month + year). A month needs a non-draft campaign (400 `CAMPAIGN_NOT_STARTED`), must lie inside the campaign's dates (400 `MONTH_OUTSIDE_CAMPAIGN`) and not in the future (400 `FUTURE_PERIOD`); clicks ≤ impressions and conversions ≤ leads (400 `INVALID_RESULTS`, plus table CHECKs). A recorded month is added once (409 `MONTH_EXISTS` without `version`) and then corrected with its version; corrections follow the ranking rule via `MarketingMonths` (current and previous month, a Super Admin any past month, 409 `MONTH_LOCKED`), audited with `closedMonth` when a closed month changes. A closed month that was never recorded can still be added late. Once results exist the campaign cannot go back to DRAFT or be deleted (409 `CAMPAIGN_HAS_RESULTS`), and its dates must keep covering the recorded months (409 `RESULTS_OUTSIDE_DATES`). Rates (CTR = clicks ÷ impressions, CPL = spend ÷ leads: ₹42,000 ÷ 84 = ₹500, conversion = conversions ÷ leads, plus cost per click) come from summed results, never averaged; remaining budget = budget − lifetime spend and may go negative (`overBudget`). The CSV import only adds months (campaign matched by external id, else a unique name). The LinkedIn Campaigns target counts campaigns with results recorded in the month. Migration V13 is the paid part of the original V12.
- **Leads count in the month of their lead date** towards the Website Leads target (`LEADS`, every lead, any status) and their source's target (`LEADS_BY_SOURCE`). So a lead's date and source can only change, and a lead can only be deleted, while its month is open (current or previous business month; a Super Admin any past month, audited with `closedMonth`), 409 `MONTH_LOCKED`; future dates are rejected (400 `FUTURE_LEAD_DATE`). Contact details, status, owner, link and notes stay editable in any month. A lead names at most one campaign or content item (400 `ONE_LINK`, plus a table CHECK), of the kind its source takes (`LeadRules`: EMAIL → sent email campaign, LINKEDIN/PAID_CAMPAIGN → non-draft paid campaign, LinkedIn leads only LinkedIn campaigns, BLOG → published content; otherwise 400 `LINK_NOT_ALLOWED` / `INVALID_LINK`), and never dated before it was sent, started or published (400 `LEAD_BEFORE_LINK`). Campaigns that leads name stay consistent: they cannot be deleted, an email campaign stays SENT and a paid campaign never returns to DRAFT, and neither can move after its first lead (409 `CAMPAIGN_HAS_LEADS`); the FKs are RESTRICT as a backstop. Leads are shared across the marketing team (LEAD_VIEW sees all, like SEO); lead targets appear in the lead summary only for TARGET_VIEW holders. The `marketing-leads` CSV import follows the same rules, matches the `campaign` column by the source's link kind (external id or URL, else a unique name), and rejects an `external_id` already imported or an email already recorded on the same date; each imported lead is audited. Lead checks shared with the importer run with `noRollbackFor = ApiException`, so a rejected row never rolls back the import. **Migration numbering**: V14 is `content_items` and V15 `marketing_leads`; backlinks get their own migration in Phase 17 and the monthly reports table moves on accordingly.
- **Backlinks count each stage in the month of its own date** (submitted, approved, live, rejected, lost), so a link submitted in September and live in October counts in both months, and a later loss never lowers a closed month: lost is a dated stage of its own. The Backlinks target (`BACKLINKS_LIVE`) counts links that went live in the month. **Remaining follows brief §46: max(target − submitted, 0)**, what is still to be submitted (50 − 35 = 15); the target's own achievement stays live ÷ target (22 of 50 = 44%, 28 to go live). Each status needs the dates of its stages and allows no later ones (`BacklinkRules`: SUBMITTED → submitted; APPROVED → submitted + approved; LIVE → submitted + live, approval optional; REJECTED → submitted + rejected; LOST → submitted + live + lost), in order, never in the future (400 `MISSING_DATE` / `DATE_NOT_ALLOWED` / `DATE_ORDER` / `FUTURE_DATE`), and a live or lost link needs its URL (400 `LINK_URL_REQUIRED`). **The month lock is per date**: a stage date can only be set, moved or cleared while its old and new months are open (current or previous month; a Super Admin any past month, audited with `closedMonth`), 409 `MONTH_LOCKED`; so a link submitted in a closed month can still go live or be lost today, and `lockedDates` tells the client which dates are fixed. Deleting needs every stage month open. The target is an SEO page or a URL/site path (the page's URL when only the page is given); the referring domain defaults to the link URL's host (lower case, no `www.`). A second backlink from the same link URL to the same target is rejected (409 `DUPLICATE_BACKLINK`, checked in the service: the URLs are too long for a unique index). Backlinks are shared across the marketing team like SEO; the target and remaining appear only for TARGET_VIEW holders. Owner filters narrow the counts but the target stays the team's. Migration V16 is backlinks; the monthly reports table moves to a later number.
- **Content counts by publication month while it is live.** PUBLISHED and UPDATED items count in the month of their publication date (a refresh never moves them; the refreshed date is its own monthly figure); the Blogs Published target (`BLOGS_PUBLISHED`) counts live items of type BLOG only. **Remaining follows brief §48: max(target − published, 0)** (12 − 9 = 3). Blogs *planned* for a month count by the new `planned_date`, whatever their status ("how many blogs planned?", brief §81). Live content needs its URL and publication date, which is never in the future (a post scheduled for later stays a draft with a planned date); an UPDATED item also needs its refreshed date, on or after publication; content that is not live has neither date (400 `CONTENT_URL_REQUIRED` / `MISSING_DATE` / `DATE_NOT_ALLOWED` / `FUTURE_DATE` / `DATE_ORDER`). Where an item counts (live or not, publication date, type while live, refreshed date) only changes while every month involved is open (Super Admin: any past month, audited with `closedMonth`), 409 `MONTH_LOCKED`; `publicationLocked` / `refreshLocked` tell the client. Content that leads name stays live and is never published after its first lead, and cannot be deleted (409 `CONTENT_HAS_LEADS`). URLs are unique among content items (409 `DUPLICATE_URL`), since the lead import matches content by URL. **Content leads** are the leads that name a content item, counted by lead date and filtered by the content's owner; the Blog Leads target (BLOG-source leads) is shown beside them. The brief's §48 example (45 leads) conflicts with §44 (20 blog leads in October); the seed follows §44. Organic traffic and CTA clicks stay hand-entered totals per item (not monthly). Content attachments (brief §64) use V18 `content_item_attachments` and the shared FileService. No content CSV import: brief §53 does not list content.
- **The marketing dashboard is one endpoint** (`/api/marketing/dashboard`) built from the modules' own aggregate queries, not a separate copy of their rules: each module's monthly query runs once over the trend range and serves the month, the comparison month (always the month before, brief §50) and the trend. Sections are omitted (null) without the module's view permission and targets without TARGET_VIEW, so the endpoint never shows more than the module pages would. The owner filter narrows each module's records to their owner (activities: the occurrence's assignee, as in the occurrence list); the lead, backlink and blog targets stay the team's, while the target list shows the owner's targets. LinkedIn figures cover LinkedIn campaigns only (brief §22). Activity completion % = completed ÷ (due − skipped). `TargetActualSource.actualsFor` lets types that share a source share a query. The home dashboard's marketing summary for Rakesh (brief §8.9) will read this endpoint in the frontend.
- **The `email-campaigns` CSV import** creates SENT campaigns with provider CSV; `external_id` (e.g. the Zoho campaign id) is unique per provider, so the same campaign cannot be imported twice. Blank bounces default to sent − delivered and blank total opens/clicks to the unique counts. `ManualEmailCampaignProvider` stays the data source until a Zoho integration (provider ZOHO) is added.
- **`/digital-marketing` is the executive dashboard** since Phase 19; the Phase 9 home's rating legend, data sources and imports live on below it. The home dashboard's marketing summary shows on the company-wide (Super Admin) dashboard to MARKETING_VIEW holders, from the same endpoint.

## Phase 2a: Technology decisions

**Backend**: Java 21 and **Spring Boot 4.x, latest GA**, with the exact patch confirmed on start.spring.io / Maven Central when Phase 3 scaffolds the project. Maven with the wrapper.
- Starters: web, security, **oauth2-resource-server** (Spring Security's built-in Nimbus `JwtEncoder`/`JwtDecoder`, HS256, so no third-party JWT library), data-jpa, validation, **flyway** (`spring-boot-starter-flyway` is a separate starter in Boot 4) + `flyway-mysql`, actuator. Plus `mysql-connector-j`, Lombok, MapStruct (entity→DTO), springdoc-openapi, and Apache Commons CSV.
- Auth: a short-lived access JWT (60 min) plus a **refresh token** in an httpOnly cookie, stored hashed in `refresh_tokens`. This gives real logout/revocation and session expiry. Passwords use BCrypt with strength 12.
- Authorization works on three layers:
  1. `@PreAuthorize` with permission authorities such as `TASK_EDIT` and `SEO_EDIT`.
  2. An `AccessScopeService` that turns the current user into a data scope: ALL for Super Admin, the department IDs a manager runs, or OWN for employees. Repository Specifications and queries apply that scope.
  3. The backend computes the user, role, department and permissions from the DB on every request. JWT claims are only a cache that gets re-validated.
- Env loading: `spring.config.import=optional:file:.env[.properties]` in `application.yml`. Boot reads `backend/.env` natively, with no extra dependency. Properties look like `spring.datasource.password=${DB_PASSWORD}`.
- Profiles: `dev` turns on the dev seeder and verbose SQL. `test` uses Testcontainers MySQL, falling back to the local DB if Docker is missing. `prod` is the default.
- JPA: `ddl-auto=validate` (Flyway owns the schema). `open-in-view=false`. UTC everywhere (`hibernate.jdbc.time_zone=UTC`). Batch fetching and `@EntityGraph` prevent N+1 queries. Dashboards use dedicated aggregate native/JPQL queries that return projections.
- Integration seams (interfaces now, manual implementations only): `FileStorageService` (`LocalFileStorageService`, with S3/SharePoint later), `SeoRankingProvider` (`ManualSeoRankingProvider`), `EmailCampaignProvider`, `PaidCampaignProvider`, `AnalyticsProvider`, `LeadProvider`, and `ReportExporter` (CSV now, PDF later).

**Frontend**: React 19, TypeScript (strict), Vite, React Router, Tailwind CSS v4, shadcn/ui (Radix), Lucide, Recharts, React Hook Form + Zod, Axios (an interceptor attaches the token and handles silent refresh on 401), TanStack Query, and sonner toasts. Every route is lazy-loaded. Tests use Vitest + Testing Library. `frontend/.env` holds only `VITE_API_BASE_URL`, which is not a secret.

## Phase 2c: MySQL schema

**Conventions**: InnoDB, `utf8mb4` / `utf8mb4_0900_ai_ci`. PK `id BIGINT UNSIGNED AUTO_INCREMENT`. `created_at`/`updated_at DATETIME(6)` in UTC. Enums are stored as `VARCHAR(32)` and mapped with `@Enumerated(STRING)`, so adding a value needs no `ALTER`. Monetary values use `DECIMAL(14,2)` with `currency CHAR(3) DEFAULT 'INR'`. `version INT` is an optimistic lock on tasks, tickets, targets and approvals. Every FK column and every common filter column gets an index. **Derived values are never stored**: remaining, achievement %, target status, ranking colour, open/click/CTR/CPL rates, workload %, SLA state and project progress are all computed in services.

Human-readable codes (`TSK-000001`, `TKT-000001`, `PRJ-0001`, `APR-000001`, `LEAD-000001`) come from the `code_sequences` table, using `SELECT … FOR UPDATE` in the same transaction so codes never collide.

## Phase 2d: Key business-rule decisions
- **Workload %** = remaining estimated hours of active tasks (TODO/IN_PROGRESS/BLOCKED/IN_REVIEW) due within the workload window (default 14 days, overdue included) ÷ (weekly_capacity_hours × window weeks) × 100. Remaining hours = max(estimated − actual, 0). An unestimated task counts as `default_task_hours` (default 4). Levels: ≤40 LOW, ≤70 NORMAL, ≤100 HIGH, >100 OVERLOADED.
- **Target status**: actual ≥ target → ACHIEVED (green). Achievement % < threshold (default 60%, set globally or per type) → BEHIND (red). Otherwise IN_PROGRESS (orange). Remaining = max(target − actual, 0).
- **SEO**: positions 1–10 are TOP_10 (green), 11–100 are RANKING (orange), NULL is NOT_RANKED (red). Change = previous − current, so a positive number means improved. Every status carries a label and icon, never colour alone.
- **SLA**: due timestamps are snapshotted at ticket creation. State is ON_TRACK, WARNING (≥ warning % elapsed) or BREACHED. The clock pauses while a ticket is WAITING_FOR_REQUESTER.
- All rate formulas follow brief §80. Division by zero returns `null`, which the UI shows as "—".
